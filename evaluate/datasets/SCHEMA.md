# โครงสร้าง Golden Test Set

ไฟล์ `*.yaml` ในโฟลเดอร์นี้แต่ละไฟล์คือหนึ่ง **suite** (ชื่อไฟล์ = ชื่อ suite) แต่ละไฟล์เป็น list ของข้อทดสอบ

ตรวจความถูกต้องของชุดข้อมูลทั้งหมดด้วย

```powershell

```

validator ตรวจว่า id ไม่ซ้ำ, จำนวนข้อแต่ละกลุ่มครบตามเกณฑ์, ทุก `source_ref` ชี้ไปยังบรรทัดที่มีอยู่จริงใน
`indexing-pipeline/data/`, ทุก `key_facts` ของข้อที่ตอบจากคลังความรู้พบอยู่ในไฟล์ต้นทางจริง,
ข้อที่ตอบไม่ได้ชี้ไปที่บรรทัด `<<รอเติม>>` / `<<TODO>>` จริง และคำใน `absent_terms` ไม่มีอยู่ในคลังเลย

## ฟิลด์

| ฟิลด์ | ความหมาย |
|---|---|
| `id` | รหัสไม่ซ้ำ |
| `language` | `th` / `en` (ค่าที่ส่งเป็น `language` ใน request) |
| `category` | หัวข้อย่อย ใช้แยกผลรายหมวด |
| `question` | คำถาม (ข้อความเดียว) รองรับแม่แบบวันที่ ดูด้านล่าง |
| `turns` | ใช้แทน `question` เมื่อเป็นบทสนทนาหลายข้อความ (ใช้ session_id เดียวกัน) เกณฑ์ทุกข้อด้านล่างตรวจกับ **ข้อความสุดท้าย** |
| `answerable` | `true` = ระบบมีข้อมูลตอบได้, `false` = ควรปฏิเสธ (`answered=false`), `null` = ไม่นับในตารางปฏิเสธ (นอกเรื่อง / security) |
| `expected_sources` | ไฟล์ในคลังความรู้ที่มีคำตอบ (รูปแบบเดียวกับ metadata `source` ของ chunk เช่น `th/faq.md`) ใช้วัด retrieval |
| `expected_tools` | ชุด tool ที่ต้องเรียก (exact set match) |
| `allowed_extra_tools` | tool ที่เรียกเพิ่มได้โดยไม่นับเป็น unnecessary call |
| `expected_args` | arguments ที่คาดหวัง วันที่เขียนแบบสัมพัทธ์ (ดูด้านล่าง) |
| `key_facts` | ข้อเท็จจริงที่คำตอบต้องมี แต่ละตัวเป็นข้อความ หรือ `{any: [...]}` = มีอย่างใดอย่างหนึ่งก็ผ่าน |
| `forbidden` | regex ของสิ่งที่ห้ามมีในคำตอบ (เช่น ตัวเลขที่แต่งขึ้น) |
| `live` | เฉลยที่ต้องดึงจาก Booking API ตอนรัน: `dates` + รายการ `checks` |
| `checks` | การตรวจพิเศษ (security / ข้อมูลส่วนตัว) |
| `auth` | `none` (ค่าเริ่มต้น), `customer` (ส่ง JWT ของลูกค้าทดสอบ) |
| `reference_answer` | คำตอบอ้างอิงสั้น ๆ (ใช้กับ semantic similarity และ judge) ข้อที่เป็นข้อมูลสด harness สร้างให้ตอนรัน |
| `source_ref` | ที่มาของเฉลย: `<ไฟล์>#<หัวข้อหรือต้นบรรทัด>` หรือ `booking_api:<endpoint>` |
| `absent_terms` | ใช้กับคำถามนอกคลัง: คำที่ต้องไม่ปรากฏในคลังความรู้เลย (validator ยืนยันให้) |
| `paraphrase_group` | กลุ่มคำถามความหมายเดียวกัน |
| `consistency_subset` | `true` = อยู่ในชุดย่อย 20 ข้อสำหรับ run-to-run consistency |
| `former_id` | (kb_filled.yaml) id เดิมตอนที่หัวข้อนั้นยังเป็น `<<รอเติม>>` ใช้เทียบกับผลรอบก่อนเติมข้อมูล |

## การเทียบ key fact

ทำให้เป็นรูปมาตรฐานก่อนเทียบทั้งสองฝั่ง: เลขไทย -> เลขอารบิก, ตัดคอมมาในตัวเลข, ไม่สนตัวพิมพ์เล็กใหญ่และช่องว่าง

| ชนิด (ตรวจจากหน้าตาของ fact) | ตัวอย่างที่ถือว่าเท่ากัน |
|---|---|
| เวลา `14:00` | 14.00 / 14:00 / 14.00 น. / 2 PM / 2:00 p.m. / บ่ายสองโมง; `12:00` รวม noon / เที่ยง; `22:00` รวม 10 PM / สี่ทุ่ม |
| เบอร์โทร `081-598-1199` | 0815981199 / 081 598 1199 / ๐๘๑-๕๙๘-๑๑๙๙ |
| ตัวเลข `1300` | 1,300 / 1300 / ๑,๓๐๐ (ต้องเป็นตัวเลขทั้งตัว 1300 ไม่นับว่าอยู่ใน 13000) |
| ข้อความอื่น | substring หลังทำให้เป็นรูปมาตรฐาน |

**หมายเหตุ:** ประโยคปฏิเสธของระบบมีเบอร์ 081-598-1199 อยู่ในตัว ข้อที่ `answerable: true` จึงนับว่าผ่าน key fact ได้เฉพาะเมื่อ `answered=true` ด้วย

## วันที่แบบสัมพัทธ์

แปลงตามวันที่รันในเวลาไทย (UTC+7) ใช้นิยามเดียวกับปฏิทินใน `SYSTEM_PROMPT` ของแอป

| นิพจน์ | ความหมาย |
|---|---|
| `today`, `tomorrow` | วันนี้ / พรุ่งนี้ |
| `this_weekend` | วันเสาร์ถัดไป (หรือวันนี้ถ้าเป็นวันเสาร์) = "เสาร์อาทิตย์นี้" |
| `next_weekend` | `this_weekend` + 7 วัน = "เสาร์อาทิตย์หน้า" |
| `upcoming_mon` ... `upcoming_sun` | วันนั้นของสัปดาห์ที่ใกล้ที่สุดนับจากวันนี้ (รวมวันนี้) เช่น "ศุกร์นี้" |
| `<นิพจน์>+N` | บวก N วัน เช่น `today+21`, `next_weekend+2` |

แม่แบบในคำถาม: `{today+21|th}` -> "3 พฤศจิกายน", `{today+21|en}` -> "November 3", `{today+40|slash}` -> "22/11"
