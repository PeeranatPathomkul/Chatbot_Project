# Indexing Pipeline — แชทบอท RAG รีสอร์ท (ภาษาไทย)

Pipeline สำหรับแปลงเอกสารรีสอร์ทภาษาไทย (นโยบาย / FAQ / ราคา / ประเภทห้อง)
ให้กลายเป็น vector store ที่ค้นหาด้วยความหมายได้ พร้อมสำหรับต่อกับขั้นตอน
Retrieval + Generation (Typhoon 2.1) ในภายหลัง

**ขอบเขตของโปรเจกต์นี้:** เฉพาะส่วน Indexing เท่านั้น — ยังไม่มี API และยังไม่เรียก LLM

| ส่วนประกอบ | ที่ใช้ |
|---|---|
| Text splitter | LangChain `RecursiveCharacterTextSplitter` (ตั้ง separators สำหรับไทย) |
| Embedding | `intfloat/multilingual-e5-base` (768 มิติ) ผ่าน sentence-transformers |
| Vector DB | ChromaDB `PersistentClient` — distance metric = **cosine** |
| Python | 3.10+ (พัฒนาและทดสอบบน 3.11.9 / Windows 11) |

## เพิ่มเอกสารของคุณเอง

วางไฟล์ `.md` หรือ `.txt` ลงใน `data/` แล้วรัน `python -m src.indexer` — จบ

การระบุหมวดหมู่ทำได้ 3 ทาง (ไล่ลำดับความสำคัญ):

1. **YAML front matter** ที่หัวไฟล์ — วิธีที่แนะนำ
   ```markdown
   ---
   category: ห้องพัก
   title: ประเภทห้องพัก
   ---

   # เนื้อหา...
   ```
2. **mapping ตามชื่อไฟล์** ใน `config.CATEGORY_BY_FILENAME` — เหมาะกับไฟล์ `.txt` ที่ใส่ front matter ไม่ได้
3. **ค่าเริ่มต้น** `config.DEFAULT_CATEGORY` = `"ทั่วไป"`

การใส่หัวข้อ `##` ในไฟล์ช่วยคุณภาพมาก เพราะ pipeline จะตัดตามหัวข้อก่อนเป็นอันดับแรก
(ดูหัวข้อถัดไป)

## การออกแบบ: ทำไมถึงเลือกค่านี้

### ทำไม `chunk_size = 450` ตัวอักษร

- นับเป็น **ตัวอักษร** ไม่ใช่ token เพราะภาษาไทยไม่มีช่องว่างระหว่างคำ
  การนับคำแบบ whitespace จึงไม่มีความหมาย
- วัดจากคลังเอกสารจริง: tokenizer ของ e5 (XLM-RoBERTa) ให้ **1 token ≈ 3.5 ตัวอักษรไทย**
  ดังนั้น 450 ตัวอักษร ≈ 127 token ซึ่งห่างจากเพดาน **512 token** ของโมเดลมาก
  (ถ้าเกินเพดาน โมเดลจะตัดข้อความส่วนเกินทิ้ง **เงียบ ๆ** โดยไม่มี error — เป็นบั๊กที่จับยากมาก)
- เอกสารประเภท FAQ/นโยบายมีคำตอบต่อหนึ่งประเด็นราว 100–350 ตัวอักษร
  ขนาด 450 จึงเก็บ "หนึ่งประเด็นจบในตัว" ได้พอดี ไม่เล็กจนคำตอบขาดครึ่ง
  และไม่ใหญ่จนหนึ่ง chunk ปนหลายเรื่องแล้วเวกเตอร์ถูกเฉลี่ยจนจับใจความไม่ได้
- ผลจริงที่ได้: 27 chunk จาก 5 ไฟล์ — เล็กสุด 148 / มัธยฐาน 342 / ใหญ่สุด 475 ตัวอักษร

### ทำไม `chunk_overlap = 90` ตัวอักษร (20%)

เผื่อกรณีที่ประโยคสำคัญถูกตัดคาบเกี่ยวรอยต่อ chunk เช่นเงื่อนไข
"ยกเลิกล่วงหน้า 7 ถึง 14 วัน คืนเงิน 50 เปอร์เซ็นต์" ถ้าถูกผ่ากลางพอดี
จะไม่มี chunk ไหนมีข้อความนี้ครบเลย — การซ้อน 20% ทำให้ยังมีอย่างน้อยหนึ่ง chunk
ที่เก็บประโยคนั้นไว้เต็ม ๆ ค่านี้เป็นจุดสมดุลมาตรฐาน: น้อยกว่านี้เสี่ยงข้อมูลขาด
มากกว่านี้เปลืองพื้นที่และทำให้ผลค้นหาซ้ำกันเอง

### ทำไม separators ชุดนี้ (หัวใจของการรองรับภาษาไทย)

```python
["\n\n", "\n", "। ", "? ", "! ", ". ", "ฯ ", " ", ""]
```

`RecursiveCharacterTextSplitter` จะไล่ลองตัวคั่นจากตัวแรกไปตัวสุดท้าย
ถ้าตัวคั่นแรกยังทำให้ chunk ใหญ่เกินไปจึงค่อยลองตัวถัดไป เรียงจาก
"ขอบเขตความหมายใหญ่" ไป "เล็ก" — ตัวที่สำคัญที่สุดคือสองตัวนี้:

- **`"\n"` (ขึ้นบรรทัด)** — เอกสารไทยแบบ FAQ และ bullet list แบ่งประเด็นด้วยบรรทัด
  การตัดตรงนี้แทบไม่เสียความหมายเลย
- **`" "` (เว้นวรรค)** — จุดสำคัญที่สุด **ภาษาไทยไม่เว้นวรรคระหว่าง "คำ"
  แต่เว้นวรรคระหว่าง "วลี/ประโยค"** การเว้นวรรคจึงเป็นขอบเขตความหมายที่ปลอดภัย
  ตรงข้ามกับภาษาอังกฤษที่เว้นวรรคคือขอบเขตของคำ

ค่าเริ่มต้นของ LangChain (`["\n\n", "\n", " ", ""]`) ใช้กับไทยได้ในระดับหนึ่ง
แต่จะตกไปที่ `""` (ตัดตามตัวอักษร) เร็วกว่าที่ควร ซึ่งเป็นตัวที่ **ตัดกลางคำ**
ชุดนี้จึงแทรกตัวคั่นระดับประโยคเพิ่มเพื่อเลื่อนโอกาสตกไปถึง `""` ให้น้อยที่สุด

### ตัดตามหัวข้อ markdown ก่อนเป็นอันดับแรก

ก่อนเรียก text splitter เราแบ่งเอกสารตามหัวข้อ (`#`, `##`) ก่อน
เพื่อไม่ให้ chunk เดียวคร่อมสองหัวข้อที่ไม่เกี่ยวกัน — เช่นท้ายเรื่อง "Superior Room"
ไปติดกับต้นเรื่อง "Deluxe Room" ซึ่งจะทำให้แชทบอทตอบผิดห้องได้ง่ายมาก

### บรรทัดบริบทหัว chunk (contextual chunk header)

ทุก chunk จะถูกเติมบรรทัดนี้ก่อนนำไป embed:

```
[หมวด: ห้องพัก | หัวข้อ: Deluxe Room (ดีลักซ์)]
ห้อง Deluxe สามารถขอเตียงเสริมได้ 1 เตียง คิดค่าบริการเตียงเสริมคืนละ 800 บาท ...
```

เพราะ chunk ที่ถูกตัดออกมากลางเอกสารมักสูญเสียบริบทว่า "กำลังพูดถึงอะไรอยู่"
เช่น chunk ที่เขียนว่า "ขอเตียงเสริมได้ 1 เตียง" เพียว ๆ จะไม่รู้ว่าหมายถึงห้องไหน
ปิดได้ด้วย `RESORT_PREPEND_HEADING=0` (บรรทัดนี้จะถูกตัดออกตอนแสดงผลให้คนอ่านเสมอ)

### ทำไมต้องเป็น cosine

```python
collection = client.get_or_create_collection(
    name=..., metadata={"hnsw:space": "cosine"}   # ค่าเริ่มต้นของ Chroma คือ l2
)
```

ค่าเริ่มต้นของ ChromaDB คือ **L2 (Euclidean)** ถ้าไม่ระบุ ผลการจัดอันดับตอน retrieval
จะไม่ตรงกับที่ออกแบบไว้ ค่านี้ถูก "ตรึง" ตั้งแต่ตอนสร้าง collection **เปลี่ยนทีหลังไม่ได้**
ถ้าเผลอสร้างผิดต้องใช้ `--reset`

เวกเตอร์ทุกตัวถูก normalize ให้ยาว 1 (`normalize_embeddings=True`) จึงเข้าคู่กับ cosine พอดี
และแปลงกลับเป็นคะแนนที่อ่านง่ายได้ตรง ๆ: `similarity = 1 - distance`

### prefix ของโมเดลตระกูล e5

โมเดล e5 เทรนมาแบบ asymmetric — **ต้อง** ใส่ prefix คนละอันระหว่างเอกสารกับคำถาม:

```python
embed_documents(texts)  ->  "passage: " + text     # ตอน index
embed_query(text)       ->  "query: "   + text     # ตอนค้นหา
```

`src/embedding.py` เป็น **ที่เดียว** ในโปรเจกต์ที่แตะ prefix และแยกเป็น 2 ฟังก์ชันชัดเจน
เพื่อกันการเรียกผิดด้าน — ซึ่งเป็นบั๊กที่พบบ่อยและไม่แสดง error ใด ๆ แค่ผลค้นหาแย่ลงเงียบ ๆ

ผลวัดจริงบนคลัง 27 chunk × 6 คำถาม (จาก `thai_smoke_test`):

| รูปแบบ prefix | top-1 ถูกไฟล์ | margin เฉลี่ย |
|---|---|---|
| **ถูกด้าน (query:/passage:)** | 5/6 | **0.0441** |
| สลับด้าน (passage:/query:) | 5/6 | 0.0329 |
| ไม่ใส่ prefix เลย | 5/6 | 0.0404 |

`margin` = ช่องว่างระหว่างคะแนนของ chunk ที่เกี่ยวข้องที่สุด กับ chunk ที่ไม่เกี่ยวข้องที่สุด
ยิ่งกว้างยิ่งแยกแยะได้เด็ดขาด — ที่ไม่ดูคะแนนดิบเพราะ e5 ให้คะแนนคู่ข้อความไทยสูง
0.8–0.9 แทบทุกคู่อยู่แล้ว สิ่งที่ retrieval ต้องการคือ "อันดับ" ที่ถูก ไม่ใช่ตัวเลขที่สูง

> บนคลังเล็กขนาดนี้ ความต่างยังไม่มาก และ "ไม่ใส่ prefix" ก็ได้ตัวเลขใกล้เคียง
> ข้อแตกต่างจะชัดขึ้นเมื่อคลังใหญ่และคำถามกำกวมมากขึ้น เราทำตาม model card ไว้ก่อน

## การ re-index: รันซ้ำแล้วต้องไม่มีข้อมูลซ้ำซ้อน

ใช้ **สองกลไกร่วมกัน** เพราะกลไกเดียวยังมีช่องโหว่:

**1. Deterministic ID** — `chunk_id` = `<ชื่อไฟล์>::<ลำดับ chunk>` เช่น `faq::0003`
เนื้อหาเดิมรันซ้ำกี่รอบก็ได้ ID ชุดเดิม เมื่อใช้ `collection.upsert()` ระเบียนเดิม
จะถูก **เขียนทับ** แทนที่จะเพิ่มใหม่

**2. ลบตามไฟล์ก่อนเขียน (delete-by-source)** — ข้อ 1 ยังมีช่องโหว่หนึ่งอย่าง:
ถ้าแก้ไฟล์ให้ **สั้นลง** จนจำนวน chunk ลดจาก 10 เหลือ 6 ระเบียน `faq::0006`–`faq::0009`
ของรอบก่อนจะค้างอยู่เป็นข้อมูลเก่าที่ไม่มีอยู่ในเอกสารแล้ว และยังถูกค้นเจอได้
ทุกครั้งก่อน index ไฟล์หนึ่ง จึงลบ chunk ทั้งหมดที่ `source` ตรงกับไฟล์นั้นก่อนเสมอ

ผลลัพธ์: **collection สะท้อนเนื้อหาปัจจุบันของ `data/` เสมอ** ไม่ว่าจะรันกี่รอบ
(มีเทสต์ครอบทั้งสองเคสใน `tests/test_indexer.py`)

**เมื่อไหร่ต้องใช้ `--reset`:** เมื่อเปลี่ยน embedding model หรือ chunk_size
เพราะเวกเตอร์ชุดเก่ากับชุดใหม่เทียบกันไม่ได้ ต้องสร้างใหม่ทั้งหมด

## การทดสอบ

### `scripts/thai_smoke_test.py` — ตรวจ 5 ด้าน

| # | ตรวจอะไร | วิธีตรวจ |
|---|---|---|
| 1 | Chunking | จำนวน/ขนาด chunk + metadata ครบ + แสดงตัวอย่าง chunk จริงให้ดูด้วยตา |
| 2 | ขอบเขตคำไทย | ตรวจอัตโนมัติว่าไม่มี chunk ถูกตัดกลางคำ (ดูวิธีด้านล่าง) |
| 3 | ความยาว token | ตรวจว่าไม่มี chunk เกิน 512 token จนถูกโมเดลตัดทิ้งเงียบ ๆ |
| 4 | e5 prefix | เทียบ 3 รูปแบบ prefix บนคลังจริง วัดด้วย top-1 accuracy + margin |
| 5 | Retrieval | ยิงคำถามไทย 6 ข้อผ่าน ChromaDB จริง แสดง chunk + similarity score |

**วิธีตรวจการตัดกลางคำไทยแบบอัตโนมัติ** (`chunking.find_broken_boundaries`)
อาศัยกฎอักขรวิธีไทยที่ตรวจได้แน่นอนโดยไม่ต้องใช้ตัวตัดคำ:

- อักขระที่ **อยู่ต้นคำไม่ได้** — สระตาม/วรรณยุกต์ (`ะ ั า ำ ิ ี ึ ื ุ ู ็ ่ ้ ๊ ๋ ์ ๆ ฯ`)
  ถ้า chunk **ขึ้นต้น** ด้วยตัวเหล่านี้ = ถูกตัดกลางคำแน่นอน
- **สระหน้า** (`เ แ โ ใ ไ`) ต้องมีพยัญชนะตามหลังเสมอ
  ถ้า chunk **ลงท้าย** ด้วยตัวเหล่านี้ = พยัญชนะถัดไปถูกตัดขาด

ผลปัจจุบัน: **27 chunk ไม่พบการตัดกลางคำแม้แต่จุดเดียว**

```
  #2 score=0.8822 | booking_policy.md | เวลาเช็คอินและเช็คเอาท์

  #2 score=0.8720 | booking_policy.md | นโยบายการยกเลิกการจอง
```

**เกณฑ์ตัดสิน** ใช้ "ไฟล์ที่ตอบคำถามได้ต้องติดมาใน top-k" ไม่ใช่ "ต้องเป็นอันดับ 1"
เพราะขั้นตอน generation จะส่ง chunk ทั้ง k ชิ้นให้ LLM อ่านอยู่แล้ว
ขอแค่ chunk ที่มีคำตอบติดมาในชุดนั้น LLM ก็ตอบได้ถูก การบังคับ top-1
เป็นเกณฑ์ที่เข้มเกินความเป็นจริงของ RAG

**การอ่านคะแนน** (อ้างอิงจากพฤติกรรมของ e5 กับข้อความไทยในคลังนี้):

| ช่วงคะแนน | ตีความ |
|---|---|
| ≥ 0.88 | ตรงมาก |
| 0.84 – 0.88 | ค่อนข้างตรง |
| 0.80 – 0.84 | พอเกี่ยวข้อง |
| < 0.80 | อาจไม่เกี่ยวข้อง |

> e5 ให้คะแนนคู่ข้อความไทยสูง 0.8+ แทบทุกคู่ ดังนั้นห้ามใช้เกณฑ์แบบ
> "similarity > 0.5 ถือว่าเกี่ยว" เด็ดขาด ให้ดูที่ **อันดับ** และ **ช่องว่างระหว่างอันดับ**
> เป็นหลัก ถ้าจะทำ threshold ตัดทิ้งใน retrieval API ควรอยู่แถว 0.80

## การปรับแต่ง

แก้ค่าใน `src/config.py` หรือ override ด้วย environment variable:

| Environment variable | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `RESORT_CHUNK_SIZE` | `450` | ความยาวสูงสุดของ chunk (ตัวอักษร) |
| `RESORT_CHUNK_OVERLAP` | `90` | จำนวนตัวอักษรที่ chunk ซ้อนทับกัน |
| `RESORT_MIN_CHUNK_CHARS` | `40` | chunk ที่สั้นกว่านี้จะถูกทิ้ง |
| `RESORT_EMBEDDING_MODEL` | `intfloat/multilingual-e5-base` | โมเดล embedding |
| `RESORT_EMBEDDING_DEVICE` | อัตโนมัติ | `cpu` / `cuda` |
| `RESORT_EMBED_BATCH_SIZE` | `32` | ขนาด batch ตอน encode |
| `RESORT_DATA_DIR` | `./data` | โฟลเดอร์เอกสาร |
| `RESORT_CHROMA_DIR` | `./chroma_db` | ที่เก็บ vector store |
| `RESORT_COLLECTION_NAME` | `resort_knowledge` | ชื่อ collection |
| `RESORT_TOP_K` | `3` | จำนวนผลลัพธ์เริ่มต้น |
| `RESORT_PREPEND_HEADING` | `1` | เติมบรรทัดบริบทหัว chunk (`0` = ปิด) |
| `RESORT_LOG_LEVEL` | `INFO` | ระดับ log |

> เปลี่ยน `RESORT_CHUNK_SIZE` หรือ `RESORT_EMBEDDING_MODEL` แล้วต้อง `--reset` เสมอ

## ขั้นตอนถัดไป (ยังไม่ได้ทำในโปรเจกต์นี้)

ฟังก์ชัน `indexer.search()` มีไว้สำหรับตรวจสอบผลการ index เท่านั้น ยังไม่ใช่ Retrieval API
เมื่อจะต่อส่วน FastAPI + Typhoon 2.1:

1. ห่อ `search()` เป็น endpoint พร้อม threshold ตัดผลที่คะแนนต่ำ (แนะนำเริ่มที่ ~0.80)
2. ประกอบ chunk ที่ได้เป็น context ส่งเข้า prompt ของ Typhoon — บรรทัดบริบท
   `[หมวด: ... | หัวข้อ: ...]` มีประโยชน์ตอนนี้ เพราะช่วยให้ LLM อ้างอิงแหล่งที่มาได้
3. ใส่ guard ให้ตอบ "ไม่พบข้อมูล" เมื่อไม่มี chunk ไหนผ่าน threshold แทนการเดา

## หมายเหตุสำหรับ Windows

`src/logging_utils.py` บังคับ `stdout`/`stderr` เป็น UTF-8 ให้อัตโนมัติ
เพราะ console ของ Windows ค่าเริ่มต้นเป็น cp874/cp1252 ซึ่งจะโยน `UnicodeEncodeError`
ทันทีที่ print ข้อความไทย ทุก entry point เรียก `setup_logging()` เป็นอย่างแรก

ถ้ารันสคริปต์ของตัวเองแล้วภาษาไทยเพี้ยน ให้ตั้ง `PYTHONIOENCODING=utf-8` เพิ่ม
